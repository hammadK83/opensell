# Verification email delivery

The backend starts a MongoDB-backed verification email worker after connecting to MongoDB. Registration saves the account and an encrypted delivery job in one document, then returns `verificationEmailDelivery: "queued"`. The worker submits the message to SMTP and makes up to five automatic attempts, with backoff capped at one minute. After five attempts, a user resend restarts attempts for the same link once any active lease has expired. Resend returns a neutral response after updating MongoDB; it does not wait for SMTP. An older delivered link remains valid until SMTP accepts its replacement. A pending link can also be used if delivery was accepted just before a worker stopped.

Set `VERIFICATION_EMAIL_KEY` to 32 random bytes encoded as 64 hexadecimal characters in every backend environment. Keep it secret and consistent across backend instances. Do not rotate it while delivery jobs are pending; this version supports one key and cannot decrypt jobs written with a previous key. [`.env.example`](.env.example) lists the required variable and safe placeholders. A unique random key was generated in this workspace's ignored development environment file; production must be configured separately.

The worker uses a short MongoDB lease so another instance can retry after a crash. Each claim consumes one of the five automatic attempts before SMTP starts, so a crash can consume an attempt even if delivery is uncertain. After an abandoned fifth attempt, manual resend can restart delivery once its lease and the account cooldown have expired. A crash after SMTP accepts a message may cause that same link to be emailed again. Multiple backend instances can run the worker concurrently. Resend responses do not wait for SMTP, though database load can still make response times vary.

Verification links expire 24 hours after creation by default. Set `VERIFICATION_TOKEN_TTL_SECONDS` to a positive whole number of seconds to change this. Both queued and delivered links have their own expiry. The worker stops trying an expired queued link; a resend creates a fresh link. An older delivered link stays usable until its own expiry or SMTP accepts the replacement. Legacy links without a saved expiry are rejected; an unverified user can request a fresh link through resend.

The backend access logger redacts `token` and `verificationToken` query values in development and production, including repeated and URL-encoded parameter names. It also redacts those values from the production referrer field. Application error logs record error types or codes without the error object or stack. Configure the reverse proxy, CDN, gateway, and observability pipeline to redact or omit verification query values and referrers before their own access logs are written; this repository does not configure those upstream systems. Verify the deployed log path separately.

# Product list pagination

`GET /api/v1/products` and `GET /api/v1/products/seller/:sellerId` require authentication and accept `limit` (default 20, maximum 100) and an optional opaque `cursor`. Both list newest first by `createdAt`, then by `_id` descending when timestamps match. The seller route only returns that seller's products. The response keeps `products` and `count`, where `count` is the number of products on this page, and adds `hasMore` and `nextCursor`. `nextCursor` is `null` on the last page. Pass a non-null cursor back to the same route to continue; malformed, modified, or cross-route cursors return HTTP 400.

The cursor is signed with `JWT_SECRET`. Rotating that secret invalidates existing cursors, so clients should restart at the first page if a cursor is rejected. New products added before the current position will not appear in later pages; deletions can shorten a later page. Pagination does not provide a snapshot of a changing catalog. The backend creates indexes for the global and seller sort patterns before it starts accepting requests, including in production. The production MongoDB role must be able to create those indexes.

# Authentication request limits

Login is limited to 10 attempts per account and 30 per client IP in 15 minutes. Registration allows 5 requests per IP per hour. Verification allows 20 per IP in 15 minutes; refresh allows 30; resend allows 10. Each rejected request returns HTTP 429, a `RATE_LIMITED` error, and a `Retry-After` header. The limits and windows can be changed with the `AUTH_*` settings in [`.env.example`](.env.example).

All backend instances use MongoDB counters, so requests cannot evade limits by switching servers. Counter keys use a keyed hash of the account email or client IP. The backend creates the collection's expiry index before accepting requests; its MongoDB role must be allowed to create that index. If MongoDB cannot record a rate-limit attempt, the request fails rather than proceeding unthrottled. Each fixed window resets at the next window boundary; MongoDB removes old counters later through the expiry index.

`TRUST_PROXY_HOPS` defaults to `0`, which ignores forwarded IP headers. Set it to the exact number of trusted reverse proxies only when the backend is accessible solely through that route and the last proxy appends or overwrites `X-Forwarded-For`. If the backend is behind a proxy while this value remains `0`, clients share the proxy's IP budget. Never use an unbounded proxy trust setting: a client-controlled forwarded address would let a caller evade IP limits. Verify the production network path before changing this setting.

# Password length compatibility

New local-account passwords are limited to 72 UTF-8 bytes because bcrypt ignores input after that boundary. The shared registration schema, mobile guidance, and backend model all reject longer new passwords instead of truncating them. Login intentionally has no matching upper bound so accounts created before this policy can still authenticate with their existing password.

No existing password hashes are changed by this policy. A future password-change or account-recovery feature should require affected users to choose a password within the current limit; migrating hashes cannot recover bytes that bcrypt previously ignored.

# Refresh rotation and retry

The mobile app saves a random retry key in SecureStore before each refresh request. A rotation atomically replaces the current refresh-token hash in its MongoDB session document. The same document keeps an AES-256-GCM encrypted copy of the successor and hashes of the old token and retry key for two minutes. Repeating the old token with its matching key during that window returns the same successor; a different key or an expired window is rejected. A later rotation replaces the recovery record. Logout with either the current token or its immediately previous token revokes the session. Existing app clients that do not send a retry key still rotate, but cannot recover a lost response.

Set `REFRESH_RETRY_KEY` to a distinct, stable 32-byte hex secret in every backend environment. Every instance must share it. Do not rotate it while any two-minute retry window is active. Session rotation uses one atomic MongoDB document update and works with standalone MongoDB as well as replica sets. The mobile app retries a network failure once immediately and can retry with its saved key after a restart. Recovery after two minutes requires signing in again. F07 separately covers compromised-token replay policy.

Each rotation first saves the old token's hash in a separate consumed-token collection. MongoDB removes these fingerprints 30 days after consumption through a TTL index; the backend role must be able to create that index. A matching old token and retry key within two minutes remains an allowed recovery. A known consumed token used outside that rule, while its original lifetime is still active, revokes only the associated device session and writes an audit warning with the session ID and time. An unknown or expired token returns 401 without revoking a session. A replay after the 30-day fingerprint retention period also returns 401, but cannot be attributed to its former session. A replay during rotation cannot leave a usable successor because both operations update the same session document. Other devices remain signed in.
